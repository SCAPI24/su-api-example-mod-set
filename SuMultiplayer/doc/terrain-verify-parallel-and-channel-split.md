# 地形校验并行化 与 TCP 三通道拆分 方案

> 目标：解决快速飞行时的**掉帧与卡顿**（实测移动客户端平均 46 fps，2 秒窗口最低 18.8 fps）。
>
> 本文只写方案，**不含实现**。所有出现在这里的代码片段都是**示意**，落地时以实际源码为准。
>
> 相关文档：`chunk-digest-tiered-verify-plan.md`（分级校验与顶层 hash 的原始设计）。

---

## 1. 实测现象与已确认的因果

### 1.1 实测数据（2026-11-05，移动客户端设备）

| 指标 | 值 | 测量方式 |
|---|---|---|
| 平均帧率 | **46.0 / 46.6 / 46.6 fps** | `CmdBridge status.frameIndex` 30 秒长时测量 × 3 轮 |
| 正常窗口峰值 | 60 ~ 73 fps | 2 秒窗口 |
| 掉帧窗口谷值 | **18.8 / 22.9 / 23.0 / 26.4 / 28.8 fps** | 2 秒窗口 |
| 掉帧占比 | **9 / 40 窗口 < 35 fps（22.5%）** | 2 秒窗口连续 40 次 |
| 位置同步速率 | 恒定 **32.0 次/秒** | 日志 `posApply` 增量，**无抖动** |

**结论**：平均帧率被**周期性、1~2 秒的骤降**拉低；不是持续低帧，也不是网络收包抖动。

### 1.2 已排除的原因

| 嫌疑 | 排除依据 |
|---|---|
| 电路同步 | 用户实测确认「电路加入房间正常」；`circuitSim` 不再报阻塞 |
| 网络收包节奏 | `posApply` 每秒恒定 +160，完全平稳 |
| 音频 | 实测 `audioRecv = 810 条 / 20 分钟` ≈ **0.7 条/秒，<100 B/s**，量级可忽略 |
| LiveMap / 调试服务 | 未运行 |

### 1.3 当前摘要负载与目标流程

当前客户端每个新加载 chunk 都先算 65536 格完整摘要，再算顶层摘要；主机收到每个完整摘要后也现算一次完整摘要。两侧每帧各自最多处理 4 块，因此新块突发会让完整摘要持续占用多帧预算。新方案将新 chunk 的首次同步改为只交换顶层摘要；完整摘要保留为脚下五块的一次性最终核验，不再由顶层 hash 是否一致来决定是否计算。

目标流程分成首次同步和最终核验两类工作：

1. **新 chunk 的首次同步**：客户端只计算 256 列顶层 hash 并上报。主机读取该 chunk 的三态修改标记，并独立检查该客户端是否有 `Leaves` 标记，按下方规则发送补丁；补丁落地后，客户端重算顶层 hash 并回报确认。
2. **最终完整核验**：只对角色脚下中心 chunk 及东、南、西、北四个相邻 chunk 计算 65536 格摘要并由主机比对。每块完成这次最终核验并处理完结果后，在当前内存驻留期间不再重复；卸载后重新加载才重新具备核验资格。

三态修改标记与 `Leaves` 是两个维度：`None` = 无已记录的主机改动，`SeasonOnly` = 只有天气/季节改动，`HasContentChange` = 有玩家或其他非季节内容改动。`Leaves` 是按客户端记录的树叶季相待补标记，可与三态标记并存。主机先看三态标记，再独立处理 `Leaves`：

| 三态修改标记 | `Leaves` 标记 | 首次同步处理 |
|---|---|---|
| `None` | 无 | 比较顶层 hash；一致则完成，不一致则发 `TopLayerFix` |
| `SeasonOnly` | 无 | 比较顶层 hash；不一致则发 `TopLayerFix`，一致则不发顶层补丁 |
| `None` | 有 | **只发树叶段补丁**；不把顶层 hash 差异解释为季节变化，后续完整核验仍由脚下五块范围决定 |
| `SeasonOnly` | 有 | **总是发树叶段补丁**；若顶层 hash 不同，再于树叶段之后发 `TopLayerFix`；若顶层 hash 相同，只发树叶段 |
| `HasContentChange` | 有 | **发树叶段补丁**，并发权威整块 `ChunkResync` 覆盖非季节改动 |
| `HasContentChange` | 无 | 发完整 `ChunkResync`；顶层 hash 不用于推断深层内容一致 |

树叶段和顶层补丁应用后，客户端都要基于当前 chunk 重算顶层 hash 并向主机回报；主机确认顶层 hash 与权威值一致后，才结束本轮首次同步。确认只清除该客户端对应的 `Leaves` 待补记录；三态 chunk 修改分类是主机侧共享记录，不能因一个客户端确认就清除，否则其他客户端加载时会失去判断依据。三态标记只在其定义的 chunk/会话生命周期边界重置。此顶层确认只验证补丁已落地，不替代脚下五块的完整最终核验。

一次 17~20 块的新块突发因此只需要顶层快照和顶层 hash；昂贵的完整摘要只会排进最多 5 块的最终核验集合，不再对每个新块计算。

## 2. 口径澄清（本次核实，避免误改）

### 2.1 `DefaultRadius = 2` **不要改**（已证无效）

| 事实 | 位置 |
|---|---|
| `DefaultRadius` 只作为**连接建立瞬间**的初始值 | `TerrainSync.cs:2165` `new State { Radius = m_options.DefaultRadius }` |
| 之后被**客户端上报值覆盖** | `TerrainSync.cs:4167` `int radius = Clamp(interest.Radius)` |

客户端上报的半径来自可见范围：

```csharp
// TerrainSync.cs:1020
int radius = (int)Math.Ceiling(visibility / 16f);
```

**可见范围 120 格 → ceil(120/16) = 8 → 实际生效半径 8，订阅窗口 17×17 = 289 块。**

因此 `DefaultRadius` 从 2 改成 1 **只在客户端首帧上报前短暂生效，随后被 8 覆盖**，改了没有效果。

> 用户口径：「没实现就可以不动」→ 本方案**不改** `DefaultRadius`。

### 2.2 主机侧与客户端侧的负载位置

| 侧 | 负载 | 当前限流 | 位置 |
|---|---|---|---|
| 客户端 | 算 65536 格摘要并上报 | `ClientDigestComputationsPerTick = 4` | `TerrainSync.cs:751`、`ComputeQueuedDigests`（`:7841`） |
| 主机 | 现算 65536 格摘要并裁决 | `PendingResolvesPerTick = 4` | `TerrainSync.cs:698`、`ResolvePendingReports`（`:5001`） |
| 客户端 | 顶层 hash（256 个高度 + 256 个顶格值） | 随完整摘要计算 | `TryCaptureTopLayer`（`:7523`） |

目标负载：

| 侧 | 工作 | 范围 |
|---|---|---|
| 客户端 | 顶层 hash + 上报 | 每个新加载 chunk |
| 主机 | 按标记判定，并按需下发树叶段 / 顶层 / 内容补丁 | 每个新加载 chunk |
| 客户端与主机 | 完整 65536 格 hash，并发送给主机比较 | 角色脚下中心 chunk + 四邻 chunk；每次内存驻留至多一次 |

顶层首次同步与最终完整核验必须是不同任务类型；顶层结果不能代替完整 hash，也不能作为是否执行最终完整核验的条件。

## 3. 核心设计：并行摘要池（24 并发，20 顶层 + 4 完整）

### 3.1 为什么不能直接把 `ComputeHash` 丢进线程池

```csharp
// TerrainSync.cs:7447 —— 现状
digest.ComputePacked(packed.GetPackedCellSource(key));
```

`GetPackedCellSource` 返回的是**引擎 `TerrainChunk.Cells` 的数组引用**（不是副本）。
主线程在 `SetCellValueFast` 写同一数组，后台线程同时读 → **数据竞争**，算出撕裂的摘要
→ 误判 Mismatch → 整块回传 → 比现在更卡。

**所以必须：主线程拷贝快照 → 后台只算哈希 → 主线程取结果。**

顶层任务每个新块都需要；完整任务只给当前角色脚下中心块与四邻块。是否算完整 hash 由这个五块范围和每驻留周期的一次性状态决定，**不由顶层 hash 是否匹配决定**。

### 3.2 快照与复用（1 GB 内存基准）

完整 hash 快照 = `65536 × 4 B` = **256 KB**。顶层 hash 只需 256 个 topHeight 和对应的 256 个顶格值，共约 **2 KB**。

| 并发 | 快照总计 | 占 1 GB |
|---|---|---|
| 8 | 2 MB | 0.2% |
| 16 | 4 MB | 0.4% |
| **20（顶层槽）** | **约 40 KB** | **约 0.004%** |
| **4（完整槽）** | **1 MB** | **0.1%** |
| **合计 24** | **约 1.04 MB** | **约 0.104%** |

**内存不是瓶颈**。真正要防的是 **GC**：

```csharp
// 完整快照必须用 ArrayPool —— 256 KB 数组超过 85 KB LOH 阈值，
// 每次 new 都是大对象堆分配，频繁触发 Gen2 GC（手机端表现就是周期性卡顿）。
int[] snapshot = ArrayPool<int>.Shared.Rent(65536);
try
{
    Array.Copy(source, snapshot, 65536);   // 主线程完成
    // ... 交给后台
}
finally
{
    ArrayPool<int>.Shared.Return(snapshot);
}
```

顶层槽复用 2 KB 左右的紧凑快照，完整槽复用 256 KB 快照。**稳态下快照分配次数为 0**（池复用），这是手机端能稳住的前提。

### 3.3 成本对比

| 项 | 成本 | 执行位置 |
|---|---|---|
| 顶层快照：256 个高度 + 256 个顶格值（约 2 KB） | ≈ 0.0002 ms（10 GB/s 内存带宽） | **主线程**（必须在，保证一致性） |
| `Array.Copy` 256 KB | ≈ 0.02 ms（10 GB/s 内存带宽） | **主线程**（仅最终完整核验的 5 块范围内） |
| `ComputePacked` 65536 格 | ≈ 0.20 ms | **后台** |
| `ComputeTopLayer` 512 次访问 | ≈ 0.002 ms（快 128 倍） | 可后台 |

新 chunk 首次同步的主线程成本约为 **2 KB 快照拷贝**。完整快照拷贝只发生在脚下五块的最终核验中；4 个完整槽最多产生约 **0.08 ms** 的主线程复制成本。

### 3.4 24 个槽位的分配：20 顶层 + 4 完整摘要

用户口径：**所有新块先走顶层 hash；完整 hash 只给脚下中心块及四邻块的最终核验。池容量为 20 个顶层槽 + 4 个完整槽。**

```
┌─────────────────────── ChunkDigestPool (总并发 24) ───────────────────────┐
│                                                                          │
│  ┌── 顶层槽 × 20 ─────────────┐   ┌── 完整槽 × 4 ────────────────────┐  │
│  │ ComputeTopLayer           │   │ ComputePacked                     │  │
│  │ 512 次访问 ≈ 0.002 ms     │   │ 65536 格 ≈ 0.20 ms                │  │
│  │ 快 128 倍                 │   │ 慢但完整                          │  │
│  │                           │   │                                   │  │
│  │ 作用：**首次同步与补丁确认**│   │ 作用：**脚下五块最终完整核验**     │  │
│  │ 每个新块都计算              │   │ 与顶层结果独立，不以顶层不一致为条件 │  │
│  └───────────────────────────┘   └───────────────────────────────────┘  │
│  合计快照内存：20×2KB + 4×256KB ≈ 1.04 MB                               │
└──────────────────────────────────────────────────────────────────────────┘
```

**为什么 20:4 这个比例合理**（算术依据）：

| 场景 | 需要的槽位 |
|---|---|
| 一次突发 17~20 块新 chunk | 20 个顶层槽一次接纳这批工作；计算/快照仍受每帧预算约束 |
| 角色周围最终核验集合 | 中心 + 四邻共 5 块；4 个完整槽并行处理，剩余 1 块排队等待槽位 |
| 顶层槽成本 | 20 块 × 约 2 KB = 约 40 KB 主线程复制，后台各算 512 个输入值 |
| 完整槽成本 | 最多 4 块并行复制 1 MB；单块完整 hash 约 0.20 ms |

**关键收益**：新块首次同步不再计算完整 hash；完整比较固定限制在脚下五块，且每块每次内存驻留只做一次，不会因顶层相同而跳过最终核验。

### 3.5 快照拷贝量可以更省（重要优化）

顶层 hash 的输入只需要：
- 256 个 `topHeight`（从 `shafts[x + z*16] & 0xFF` 取得）
- 每列对应的一个顶格值 `cells[top + x*256 + z*256*16]`（256 个 int）

**不需要整个 256 KB！**

所以顶层槽**根本不需要 `Array.Copy` 全块**：

```csharp
// 顶层槽：主线程只拷 256 个顶格值（1 KB）+ 256 个 topHeight（1 KB）
int[] topValues = ArrayPool<int>.Shared.Rent(256);
int[] topHeights = ArrayPool<int>.Shared.Rent(256);
// 主线程按 TerrainChunk 的索引布局取 256 列：
for (int x = 0; x < 16; x++)
for (int z = 0; z < 16; z++)
{
    int column = x + z * 16;
    int top = shaftsSource[column] & 0xFF;
    topHeights[column] = top;
    topValues[column] = cells[top + x * 256 + z * 256 * 16] & 0xFFFFC3FF;
}
```

**实现约束**：现有 `ComputeTopLayer(int[] cells, int[] shafts)` 按整块索引读取原数组，不能直接传入这两个紧凑数组。并行池需要增加按 `topHeights[256]` + `topValues[256]` 计算的入口，使用与现有算法完全相同的 FNV-1a 顺序及光照掩码；两端共用该实现。

**顶层槽单块主线程成本：约 2 KB 拷贝 ≈ 0.0002 ms**（几乎为零）。

| 槽类型 | 主线程拷贝 | 后台计算 |
|---|---|---|
| 顶层 × 20 | **约 2 KB / 块** | 0.002 ms |
| 完整 × 4 | 256 KB / 块 | 0.20 ms |

**20 块新 chunk 的首次同步只需约 40 KB 顶层快照复制。**完整快照只为脚下五块的最终核验复制；4 个同时运行的完整任务复制约 1 MB（约 0.08 ms）。

### 3.6 池的接口设计（示意）

```csharp
/// 地形摘要并行池。客户端与主机**共用同一份实现**，避免两套逻辑漂移。
internal sealed class ChunkDigestPool
{
    // 顶层槽 20 / 最终完整核验槽 4（用户口径）。
    // 两类任务独立限流，完整核验不会阻塞新 chunk 的顶层同步。
    private readonly SemaphoreSlim m_topSlots = new SemaphoreSlim(20, 20);
    private readonly SemaphoreSlim m_fullSlots = new SemaphoreSlim(4, 4);

    // 完成结果回主线程（主线程泵每帧取出）
    private readonly ConcurrentQueue<DigestResult> m_completed = new ConcurrentQueue<DigestResult>();

    /// 每个新 chunk 的首次同步只提交顶层快照。
    public bool TrySubmitTopLayer(ChunkKey key, int generation, int[] cells, int[] shafts);
    /// 仅脚下中心 chunk + 四邻 chunk 可提交；每次驻留最多成功核验一次。
    public bool TrySubmitFull(ChunkKey key, int generation, int[] cells);

    /// 主线程泵每帧调用：取出已完成结果（最多 N 条）。
    public int DrainCompleted(List<DigestResult> target, int max);
}

internal readonly struct DigestResult
{
    public readonly ChunkKey Key;
    public readonly int Generation;      // 用于"块已卸载/换代"时作废
    public readonly DigestKind Kind;     // 初始顶层 / 补丁确认 / 完整最终核验
    public readonly uint Value;          // 仅 FullFinal 时有效：最终完整摘要
    public readonly uint TopHeightHash;  // 仅两种顶层结果有效
    public readonly uint TopBlockHash;
    public readonly bool Ok;
}

internal enum DigestKind : byte
{
    TopLayerInitial,
    TopLayerConfirmation,
    FullFinal
}
```

### 3.7 必须处理的四个正确性问题

| 问题 | 处理 |
|---|---|
| **块在计算期间被卸载/重载** | 结果回来时比对 `m_chunkGeneration[key]`（已有该机制，见 `OnChunkUnloaded`），不等则丢弃并计数 |
| **结果乱序** | 每个结果自带 `(Key, Generation)`，主线程按 Key 归档；同一块只接受**最新代**的结果 |
| **稳定性判定顺序** | `IsStableForDigest` 必须在**提交前**判断（主线程），不能进后台 |
| **槽位耗尽** | `TrySubmit` 返回 false → 调用方把 key 放回队列尾（FIFO 不丢），下一帧重试；累计计数以便诊断 |
| **最终核验重复** | 完整 hash 匹配后，或不匹配且权威修复完成后，记录当前内存代；只要 chunk 未卸载，即使离开再进入五块范围也不再重复 |
| **补丁确认** | 树叶段 / 顶层补丁落地后重新计算顶层 hash 并上报；确认通过只结束这次补丁同步，不代替脚下五块的最终完整核验 |

### 3.8 与现有预算的关系

现有 `ClientDigestComputationsPerTick = 4` / `PendingResolvesPerTick = 4` 的语义要**重新定义**：

| 参数 | 旧语义 | 新语义 |
|---|---|---|
| `ClientDigestComputationsPerTick` | 每帧**算** 4 块完整摘要 | 改为分别预算顶层首次同步与五块范围内的完整核验 |
| `PendingResolvesPerTick` | 每帧**算** 4 块完整摘要并裁决 | 每帧提交完整核验任务；裁决消费完成结果 |
| 新增 `DigestTopSlots = 20` / `DigestFullSlots = 4` | — | 池容量；顶层为所有新块服务，完整槽只服务五块最终核验 |
| 新增 `DigestDrainPerTick` | — | 每帧从完成队列取结果；须分别保证顶层确认和完整核验结果及时消费 |

每个 chunk 需要记录当前驻留代的最终核验状态。完整 hash 比对成功后置为已核验；`OnChunkUnloaded` 清除此状态。玩家移动造成五块集合改变时，只为尚未完成最终核验的 chunk 入队。

### 3.9 三态修改标记、Leaves 标记与两阶段协议

首次同步使用顶层 hash；它只表示 256 列顶层内容，**不得把“顶层相同”当成完整 chunk 相同**。消息要明确区分“顶层首次同步/补丁确认”和“最终完整核验”，不能用 `Hash = 0` 同时表示顶层报告和完整摘要未知。

三态修改分类记录 chunk 自上次同步后的主机侧变化类别：`None`、`SeasonOnly`、`HasContentChange`。有任何非季节内容改动就归入 `HasContentChange`，即使同一 chunk 也发生过季节改动；只有季节类改动时才归入 `SeasonOnly`。

| 标记 | 含义 | 首次同步行为 |
|---|---|---|
| `None` | 没有已记录的主机内容改动 | 顶层 hash 相同则无需补丁；不同时下发 `TopLayerFix` |
| `SeasonOnly` | 只发生天气/季节造成的顶层变化 | 顶层 hash 不同时下发 `TopLayerFix`；相同时无需顶层补丁 |
| `HasContentChange` | 有角色编辑或其他非季节内容变化 | 下发权威 `ChunkResync`；不以顶层 hash 推断深层一致 |

`Leaves` 是独立的、按客户端记录的树叶季相待补标记，不取代三态标记。它表示该客户端缺少主机已经真实写入的树叶季相变化：

| 三态标记 | 客户端有 `Leaves` | 下发顺序与完成条件 |
|---|---|---|
| `None` | 是 | 只下发树叶段；客户端应用后重算并上报顶层 hash |
| `SeasonOnly` | 是 | **总是下发树叶段**；若顶层 hash 不同，再于树叶段之后下发 `TopLayerFix`；若顶层 hash 相同，只下发树叶段。客户端应用后重算并上报顶层 hash |
| `HasContentChange` | 是 | 下发权威整块 `ChunkResync`，并发送该客户端待补的树叶段；待补修复全部落地后客户端重算并上报顶层 hash |
| 任意三态 | 否 | 按三态标记对应行为处理 |

主机只有在收到补丁后的顶层 hash、并确认它与当前权威顶层一致后，才结束首次同步并清除该客户端本次已修复的 `Leaves` 待补记录。三态 chunk 修改分类继续保留给其他客户端使用，不因单个客户端确认而清除。若待发送期间主机内容又变化，确认必须按对应的变更序号/水位判断，不能把旧补丁的确认当成最新内容已同步。此顶层确认不清除最终完整核验资格。

完整核验仅针对角色脚下中心 chunk 和四个正交相邻 chunk。客户端与主机分别计算完整 hash，客户端将摘要发给主机比较。每块完成一次最终核验后，以该客户端本次内存驻留代记录为已处理；离开该五块范围再进入不重复，只有 chunk 卸载并重新加载后才重新核验。若最终核验不匹配，主机按权威整块快照修复；权威修复完成后也将该驻留代记为已处理，不再用完整 hash 重复检查。

**实现状态**：阶段 1 和阶段 2 已落地上述流程。`TerrainBridge` 捕获真实天气/季节写入并记录 `Season` / `Content` 三态；树叶真实写入通过 `NoteLeavesMutation` 按客户端记录 `Leaves`。新块首报只进入顶层摘要池，树叶段/顶层补丁落地后通过带用途的顶层确认闭环；完整摘要只进入客户端与主机的脚下五块最终核验池。阶段 3 的独立地形 TCP 通道尚未接线，当前所有地形消息仍使用现有主连接；不能把三通道隔离描述成已完成。`TsVerify` 已废弃，不能用旧验证套件验收这套新协议。

## 4. TCP 三通道拆分

### 4.1 现状（已核实）

```
主机 TcpTerrainServer
  ├── Peer (IsCircuit = false) : **主通道** → 电路以外的全部消息
  │                              含：地形同步 / 区块回传 / 摘要上报 / 动物 / 角色 / 聊天 / 音频 / 交互
  └── Peer (IsCircuit = true)  : **电路通道** → 仅电路
      m_circuitPeers[primaryClientId] → circuitPeer
```

**问题**：地形洪峰（区块回传可达 MB 级）与动物/角色位置同步（低延迟小消息）**共用主通道**。
地形回传一爆发，同一路里排队的角色位置/交互消息就被堵在后面。

### 4.2 目标结构：三路

```
主机 TcpTerrainServer
  ├── Peer (ChannelKind.Primary) : 动物 / 角色 / 聊天 / 音频 / 交互（低延迟小消息）
  ├── Peer (ChannelKind.Circuit) : 电路（已存在）
  └── Peer (ChannelKind.Terrain) : **新增** → 地形同步 / 区块回传 / 摘要上报 / 裁决 / 顶层补丁
```

**与用户方案的差异**：用户提的是「电路 / 地形 / 音频 / 主」，本方案把**音频留在主通道**。

**理由**：实测音频 `audioRecv = 810 条 / 20 分钟 ≈ 0.7 条/秒、<100 B/s`，
它**不是洪峰的受害者也不是制造者**；为它多开一条 TCP 连接（多一套握手/绑定/重连/超时状态机）收益与成本不匹配。

> 若后续音频走高码率（VOICE-CHAT 已有独立协议），再按同一模板加第四路，成本可控。

### 4.3 复用现有的副通道机制（不需要重新设计）

电路副通道已经解决了**全部**难点，地形通道直接照搬：

| 已解决的问题 | 现有位置 |
|---|---|
| 第二次连接 + 握手（`CircuitAttach` / `CircuitAttached`） | `TerrainNet.cs:526-624` |
| 主连接 ↔ 副连接绑定（`PrimaryClientId`） | `TerrainNet.cs:592-602` |
| 副通道独立存活/死亡（`Peer.Alive`、`IsCircuit` 标志） | `TerrainNet.cs:385-398` |
| 主通道查副通道 | `m_circuitPeers`（`:405`）、`IsCircuitAttached`（`:772`） |
| 经 SOCKS5 代理连接副通道 | `TerrainNet.cs:1218-1231` |

**改造点**：把布尔 `IsCircuit` 泛化为枚举，其余逻辑保持形状：

```csharp
// 现在
public bool IsCircuit;

// 改成
public enum ChannelKind { Primary, Circuit, Terrain }
public ChannelKind Kind;
// 旧字段保留为只读派生属性，避免大面积改动：
public bool IsCircuit => Kind == ChannelKind.Circuit;
```

握手消息同理：`CircuitAttach/CircuitAttached` → 增加 `TerrainAttach/TerrainAttached`
（或在现有消息里加 `kind` 字段，**二选一，落地时定**）。

### 4.4 消息分流清单（落地时必须逐条核对）

**走地形通道**（`terrain.proto` 里的消息 + 相关控制）：

| 消息 | 说明 |
|---|---|
| `TopLayerDigestReport`（逻辑消息名） | 每个新 chunk 的顶层初报；树叶段 / 顶层补丁落地后的顶层确认也走此消息 |
| `ChunkDigestReport` | 只承载脚下中心 + 四邻五块的完整 hash 最终核验；不能用于新 chunk 首次同步 |
| `ChunkResync` | 区块回传（**MB 级洪峰的主要来源**） |
| `TopLayerFix` | 主机按三态标记与 `Leaves` 状态下发的顶层差异补丁 |
| `DigestVerdict` / `TopLayerDigestVerdict`（逻辑消息名） | 分别裁决完整 hash 比对、确认补丁后的顶层 hash；完整核验完成状态与补丁确认状态分开维护 |
| `InterestUpdate` | 兴趣范围变化 |
| `CellChange` | 主机权威格改动（小消息**高频**） |
| `ClientChunkSet` / `ChunkSnapshotRequest` 等 | 区块加载控制 |

**留在主通道**：动物、角色位置/动作、聊天、音频、交互、背包、电路之外的一切。

**走电路通道**（不变）：电路快照 / delta / 时钟。

> ⚠️ **落地风险**：`CellChange` 是高频小消息，但它在语义上属于地形**内容**，
> 必须与 `ChunkResync` **同通道保序**（否则"回传后紧跟格改动"的顺序会乱）。
> 所以它走地形通道，**不是**按"消息大小"分，而是按"语义边界"分。

### 4.5 断线与生命周期规则（必须明确）

| 场景 | 规则 |
|---|---|
| 地形通道断、主通道活 | 地形同步暂停并重连；**主通道继续工作**（角色仍在移动、聊天可用）。地形侧按现有 `NotReady` 语义处理 |
| 主通道断 | **全部断开**（地形/电路都是它的子通道，`PrimaryClientId` 绑定） |
| 电路通道断 | 只影响电路（现状已如此） |
| 重连 | 按现有电路通道的重连流程；地形通道重连后需要重新同步兴趣范围与摘要 |

### 4.6 带宽与拥塞隔离效果

| 通道 | 典型流量 | 洪峰 |
|---|---|---|
| 主通道 | 角色位置 32 次/秒 × 百字节级 ≈ 数 KB/s | 低 |
| 电路通道 | 小消息高频 | 低 |
| **地形通道** | 摘要上报数 KB/s | **区块回传 MB 级** |

拆分后，地形回传的 MB 级洪峰**不再阻塞**角色/交互消息，这正是不开新连接无法解决的（同一 TCP 内队头阻塞）。

## 5. 分阶段落地顺序

| 阶段 | 内容 | 风险 | 收益 |
|---|---|---|---|
| **1** | 拆分协议与校验状态：新块只报顶层 hash；标记驱动 `Leaves` / `TopLayerFix` / `ChunkResync`；补丁后顶层确认；脚下五块做一次完整 hash 最终核验 | 中高 | 新块不再逐块做 65536 格摘要；保留深层差异最终检验 |
| **2** | 并行摘要池（20 顶层 + 4 完整）：紧凑顶层快照 + 五块范围完整快照，客户端与主机都异步计算 | 中 | 限制主线程复制和摘要计算突发 |
| **3** | TCP 第三路（地形） | 中高 | 待后续单独接线；当前实现仍使用现有主连接 |

**建议按 1 → 2 → 3 顺序**：先让同步语义和完整核验边界正确，再并行化实际需要的两类摘要，最后拆分 TCP 通道。

## 6. 验收标准

| 指标 | 现状 | 目标 |
|---|---|---|
| 平均帧率（移动客户端） | 46 fps | **≥ 58 fps** |
| 2 秒窗口最低帧率 | 18.8 fps | **≥ 45 fps** |
| `< 35 fps` 窗口占比 | 22.5% | **< 5%** |

| 补丁确认 | 现有完整摘要裁决 | 补丁后重算顶层 hash 并上报，主机确认顶层一致 |
| 快照 LOH 分配 | — | **稳态 0 次/秒**（用 ArrayPool） |
| 地形洪峰期间角色同步延迟 | 未知（共用通道） | **不受影响**（阶段 3） |

## 7. 风险与注意事项

| 风险 | 说明与对策 |
|---|---|
| **数据竞争** | 绝不让后台线程读引擎数组；必须主线程 `Array.Copy` 快照（§3.1） |
| **GC 压力** | 必须 `ArrayPool`；256 KB 数组在 LOH，频繁分配会引入新的周期性卡顿 |
| **手机线程池** | 4~8 核；用**显式** `SemaphoreSlim(20/4)` 限流，不依赖默认线程池的无界增长 |
| **结果过期** | 用 `m_chunkGeneration` 作废（已有机制）；同一块只接受最新代结果 |
| **完整核验队列积压** | 角色移动跨过五块集合边界时，只把尚未核验的驻留 chunk 入队；4 个完整槽满时保留待办，不重复排入已核验块 |
| **标记与摘要时序竞争** | 每条顶层报告和补丁确认携带主机变更水位；确认落后于该 chunk 当前水位时不清标记，继续处理最新状态 |
| **吞吐反而下降** | 顶层槽快照约 2 KB；完整槽最多并行复制 4×256 KB = 1 MB。完整快照只为角色脚下五块使用，不能扩展成所有新块的常规工作 |
| **TCP 三路的复杂度** | 复用电路副通道的现成机制（§4.3），把 `IsCircuit` 泛化为枚举，不重写握手/绑定 |
| **`CellChange` 通道路径** | 必须与 `ChunkResync` 同通道保序（§4.4），不能按消息大小随意分 |
| **诊断可观测性** | 池要有：提交数/完成数/槽位等待数/过期丢弃数；三通道各自要有独立统计（现有 `ChannelStats` 已有模板） |
