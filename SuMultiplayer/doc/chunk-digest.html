方案

加载时校验，之后靠数据消息

event-driven，不巡检

加载 → 上报哈希 → 主机比对（可播放）

一致：两边都是新的；不一致：主机回传正确内容

加载时算一次 + 切片定位（可播放）

摘要不维护；比对时只回传不同的片
摘要只在加载时算一次，不做常驻维护 客户端：块加载完算一次（实测 0.19 ms/块，跑在加载线程）→ 上报 → 之后不再碰摘要。
主机：收到上报时对那一块按需现算（同样 0.19 ms），不维护 289 块的常驻摘要表。
卸载：只把摘要丢掉（Forget()），不计算任何东西。
反例：若每帧对 289 块全量重算 ≈ 51 ms —— 直接卡帧。

校验与数据消息的分工

情形靠什么发现说明
客户端本地存档是旧的 / 上一次会话残留加载时校验哈希不同 → 主机回传整块
客户端本地生成的地形与主机不同加载时校验这正是"客户端有地形但是错的"那种情况
客户端预测后被回滚加载时校验 + 预测回执预测期给宽限窗口，回滚后哈希自然对上
块加载之后有人改了方块数据消息（改动即发）不再走比对；消息带 revision/hash，落地即 Fresh
块被卸载后再进入视野又走一次加载时校验卸载清状态 → 重载自动复检（外围圈的免费复检）
加载之后地形被改（含玩家不动时）TCP 数据消息有序可靠流：不会静默丢；失败是显式状态（Connected / Backpressured / Failed）
陷阱

两个会让哈希"永远对不上"的坑

都在引擎源码里核实过

光照必须剥离

否则重传风暴
为什么

格值 = contents + light + data。光照由两边各自重算（改动还会把 3×3 邻域降级到 InvalidLight 重新算，见 SubsystemTerrain.cs:250），时序必然不同步，会有几帧的"过渡值"。

怎么做

API 层面就不给你传光照的机会：ChunkDigest 的读取器签名是 (x,y,z) → (contents, data)，光照进不来。
引擎侧：contents = Terrain.ExtractContents(value)、data = Terrain.ExtractData(value)。

引擎自己就是这么比的 SubsystemTerrain.ChangeCell:236-237 判断"内容有没有变"时先做 Terrain.ReplaceLight(value, 0) —— 同一个口径。

家具设计索引必须规范化

否则永久误判，重传也修不好

主机没这块怎么答

三态，不允许沉默
裁决主机状态主机动作客户端动作
Match有内容且哈希相同回一个极小的确认（不传数据）标记 Fresh，记下主机哈希
Mismatch有内容但哈希不同回传该块正确内容（带主机哈希）覆盖本地，标记 Fresh
NotReady内存里没有（已卸载 / 还没加载完）先按需从存档重载；拿不到就明确回 NotReady保留未确认，按重试上限重问（不静默死等）
主机"有没有内容"的判据可以直接借引擎 TerrainChunkState > InvalidContents4 —— 这正是序列化器 TerrainSerializer23.SaveChunk:701 判断"内容可用"用的条件。

一次性上报
1.7 KiB

r=8 的 289 块 → 10 条消息（实测 DigestBatching.BytesFor(289) = 1814 B），不是每块一条。

回传载荷必须压缩
256 KiB → 4.6 KiB

整块原始 65536 格 × 4 B = 256 KiB，直接传是灾难。按列竖直 RLE：典型地形 4608 B（1.8%）、全空气 1536 B；噪声数据 RLE 反而更大 → 自动退回原始（取 min）。

摘要长度
32 bit

289 块一轮的误判率 6.7e-8。若压到 16 bit：0.44% —— 只适合做外层校验，不能当唯一判据。

状态机（5 个状态、4 条规则）

状态含义迁移
Unverified刚加载，还没校验加载 → Verifying
Verifying已上报，等裁决Match→Fresh / Mismatch→Stale / NotReady→Unverified（计数重试）
Fresh与主机一致（或已被数据消息补上）不再上报；后续改动由数据消息维持
Stale主机说不一致，等覆盖内容落地 → Fresh
（删除）块被卸载状态清空 → 重载时重新校验
规则 1

同一块只校验一次：Fresh/Verifying 期间不重复上报。

规则 2

卸载即清状态：重新加载会重新校验 —— 外围圈免费复检。

规则 3

数据消息优先：到达即 Fresh，不需要再比对。

规则 4

NotReady 有重试上限（默认 5），超限计数放弃 —— 不静默死循环。

为什么不巡检

巡检要周期性传哈希；加载时校验把成本压在"事件发生的那一刻"，稳态为 0。

和位图的关系

位图管"谁该有这块"，哈希管"手里的对不对" —— 两者不重叠。

TCP：没有静默丢弃，所以不需要兜底

新 mod 不继承旧包袱
决策取值为什么
地形通道有序可靠流（TCP）地形加载涉及主机模拟（权威生成/加载），必须稳定同步；顺序与完整性不能靠运气
静默丢弃禁止（AllowSilentDrop = false）要么到达，要么是显式失败事件 —— 没有「丢了几条还能凑合」的中间态
摘要比对只在加载时TCP 保证加载后的改动一定到达 → 不需要周期巡检、不需要校验环
卸载只丢状态不计算摘要；重载时重算一次即可
通道状态Connected / Backpressured / Failed背压必须显式：队列满 → 暂停加载新块或断开，绝不阻塞游戏帧
那摘要还负责什么？

不再是「补偿丢包」，而是保证初始状态一致：客户端本地存档可能是旧世界的、可能是它自己生成的、可能带着上次会话的预测残留 —— 这些 TCP 修不了，只有比对能发现。

TCP 的两个代价（要说清）

① 队头阻塞：一块大载荷会挡住这条连接上后面的消息 → 地形与高频状态最好分开（先全 TCP，观察后再拆）。
② 背压会传导：对端读得慢 → 发送队列积压 → 必须有上限与显式降级。

明确不继承的旧包袱（六项） ① ReliableSequenced 停滞 2 s 会主动跳号（旧实现实测日志 skipped N message(s)）→ 弃用；
② 可靠消息重传上限（MaxResends = 30）耗尽即丢 → 弃用，由 TCP 语义代替；
③ ±2 圈 / 0.5 s 校验环 / 1 s 探测冷却 → 那是为不可靠传输做的补偿，新 mod 不需要；
④ 48 条 wire 的兼容负担 + 每条消息提升 revision → 新协议从最小报文集开始；
⑤ ChunkCheckpoint 的「32 格/批 + TotalBatches + KnownRevision」整条恢复链 → TCP 上可以直接传块；
⑥ 无头端 ServerAuditLog 与 ScMP 分工写 Logs/Server → 新 mod 自己写，不共用文件名。
唯一要保留的谨慎 预测回滚仍需一套一致规则：客户端本地先应用、主机结果可能不同 —— 这不是「丢包补偿」，而是权威模型的一部分，下一轮单独定。

// Mod/SuMultiplayer/Terrain/ChunkDigest.cs —— 纯逻辑，无引擎依赖
public sealed class ChunkDigest                       // 32 bit 内容摘要
{
    public Func<int,int,int> DataCanonicalizer { get; set; }   // 家具挂这里
    public bool IncludeShafts { get; set; }                    // 两端口径必须一致
    public uint Value { get; }                                  // 0 = 未计算
    public uint SliceValue(int slice);                          // 16 片，chunk = 各片 XOR
    public void Compute(ChunkCellSource source);                // 只在加载时算一次
    public void ComputeShafts(Func<int,int,int> source);        // IncludeShafts 时
    public void Forget();                                        // 卸载：只丢状态
    public List<int> DifferingSlices(ChunkDigest other);         // 定位哪几片不同
}

public sealed class ChunkLoadVerifier                  // 加载时校验状态机
{
    public bool TryBeginVerify(ChunkKey key, uint clientHash, out DigestEntry entry);
    public static DigestVerdict Compare(uint clientHash, uint hostHash, bool hostHasContents);
    public void OnVerdict(ChunkKey key, in DigestEntry entry, uint hostHash);
    public void OnNotReady(ChunkKey key);
    public void OnResyncApplied(ChunkKey key, uint hostHash);
    public void OnDataApplied(ChunkKey key, uint hostHash);   // 加载后的差异走这条
    public void OnChunkUnloaded(ChunkKey key);                // 清状态 → 重载时复检
    public ChunkFreshness StateOf(ChunkKey key);
    public List<DigestEntry> TakePendingBatch(int maxEntries);  // 32 块/批
}
实测项结果
只在加载时算改内容不碰摘要；重算才变化；改回 → 重算得到原值
卸载只丢状态Forget() 后 HasValue=false、Value=0（不做计算）
切片定位两处改动 → 只列出片 2、片 12；chunk = 16 片 XOR
TCP 契约OrderedReliableChannel=true / AllowSilentDrop=false；通道只有 3 态
回传载荷原始 256 KiB → RLE 4608 B（1.8%）；噪声数据自动退回原始
家具规范化槽位 37 vs 91（同设计）→ 规范化后哈希相同；不同设计仍不同
单块计算0.19 ms（289 块 ≈ 51 ms → 只在加载时做）
上报带宽289 块 → 10 条消息 / 1814 B
误判率32 bit：6.7e-8　16 bit：0.44%
