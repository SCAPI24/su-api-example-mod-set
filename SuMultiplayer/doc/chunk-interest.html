主机怎么维护多个客户端的 chunk 范围

一台主机面对 N 个客户端：每个客户端的视野不同、位置一直在动。主机要维护的是「每客户端窗口 + 一张反向订阅表」， 并且必须把「客户端站在哪」的判定权握在自己手里 —— 否则最外圈一定会出现"客户端有、主机没有"。

反向订阅表怎么用

一次投影，多个客户端
数据结构键 → 值用途
正表
interestChunks		clientId → HashSet<(cx,cz)>这个客户端要哪些 chunk；重算时先按旧集合"退订"再按新集合"订阅"
位置/半径
centers / radii		clientId → (chunk, r)脏检查用：位置和半径都没变就整段跳过，不重算 289 个格子
反表
chunkSubscribers		(cx,cz) → HashSet<clientId>广播投影：一个有方块改动的 chunk，直接查到该发给谁；不用对每个玩家扫一遍
客户端上报半径
reportedRadii		clientId → r客户端只能报"我要多大"，不能报"我在哪"
为什么必须有反表 地形改动是按 tick 合批的（一次几十到上百格）。若没有反表，每批都要"遍历所有玩家 × 判断是否在窗口内"； 有反表就是"按 chunk 查出订阅者集合"，代价从 O(玩家数) 降到 O(订阅者数)，而且只算一次。

什么时候重算窗口

触发动作代价控制
主机侧该客户端位置的中心 chunk 变了退订旧集合 → 订阅新集合按 chunk 比较，不是按方块坐标比较
客户端上报的半径变了同上（整窗重算）半径夹到 1..32；上报值与上次相同则不发
客户端离开/断线释放它全部订阅，清空订阅者集合只释放它自己的，不动别人的
每网络 tick只在有地形改动要广播时顺手刷新无改动就一次脏检查都不做
半径公式（照旧实现） radius = clamp(ceil(max(visibility,16)/16), 1, 32)；窗口 = (2r+1)² 个 chunk。 视野 128 → r=8 → 17×17 = 289 个；视野 256 → r=16 → 33×33 = 1089 个。上限 32 是防"客户端要求无限范围"的硬闸。

"主机没有这个 chunk"的四种情形

对策完全不同，别混为一谈
#情形主机侧事实后果对策
A位置副本滞后：主机手上那个客户端的位置还是 100 ms 前的chunk 在存档里，只是窗口中心算偏了客户端最外圈落在主机窗口之外 → 那一圈不再收到增量窗口中心用主机权威位置 + 多算一圈余量；客户端对"最外圈"标未确认并主动请求检查点
B内存已卸载：该 chunk 没有订阅者，主机把它从内存释放了存档里有，内存没有客户端请求检查点时主机手上没数据请求到达时从存档重载再答；答不了就明确回"暂不可用"，不能沉默
C超出服务上限：客户端要的半径超过主机愿意服务的范围（上限 32 / 带宽预算）主机能加载，但不愿为它付带宽外圈永远等不到数据，客户端以为"主机坏了"夹取半径并把实际生效半径回告客户端，客户端自己收窄视野（服务端权威裁剪）
D世界本来就没有：越界 / 未生成 / 其他维度的坐标存档里也没有客户端自己生成的地形是错的预测明确回"未生成"；客户端不得把本地生成当权威
E客户端本地加载器独立：客户端自己的地形加载器按它自己的规则加载/卸载 chunk，与主机的兴趣表没有强制一致关系兴趣表里可能压根没登记过这个 chunk（没有订阅者）客户端"看着有地形"，但那是本地生成或本地缓存；别人改过的差异它完全不知道客户端对未确认的 chunk 标记并请求检查点；主机收到请求就登记订阅、回基线。永远不要假设两边的集合天然相等
最外圈为什么最危险（含一条反直觉的结论） ① 位置抖动 + 窗口边界 = 同一格反复进出（要滞回：进用 r，出用 r+1）； ② 它离中心最远，任何中心偏差都会先把外圈甩出去； ③ 它最可能撞上服务上限； ④ 客户端本地生成让"看起来有"，掩盖了"其实没确认"。
反直觉但重要的结论：靠"位置滞后"把整圈甩出去在现实中几乎不可能 —— 一个 chunk 是 16 格，8 Hz 的位置更新下要连续丢 16 个包（≈2 秒）才会偏 1 个 chunk。 所以"A 情形"更多是边界瞬时（刚跨过 chunk 边界、更新还在路上，持续 ≤1 个更新间隔，前沿那一列 chunk 短暂没有订阅者）， 而真正经常造成"客户端有、主机没有"的是 B（内存已卸载）、C（半径超服务上限）、E（客户端本地加载器独立）。

三条不变量（写进代码，不靠自觉）

① 未确认 = 预测

客户端渲染的每个 chunk 都要有一个"主机确认过的 revision"；没有就是预测，可以显示但必须可回滚、可请求。

② 判据是 revision 差

主机不问"我内存里有没有"，只问"这个客户端确认到哪一版"。内存命中与否只影响怎么答（直接发 / 重载后发）。

③ 卸载不撤销确认

主机卸载 chunk 只是释放缓存；客户端已确认的数据仍然有效，之后重新需要时从存档重载 —— 版本号必须继续单调。

这三条直接回答你的问题 "客户端位置上刚好加载了 chunk、主机没加载"是允许发生的（情形 B/D），系统不靠"永远不发生"来正确，而靠"发生时有明确答案"来正确： 要么重载后补上，要么明确告知不可用，绝不让客户端把本地预测当成权威。

判定规则表

事件要不要同步触发什么为什么
chunk 进入某客户端窗口要（一次基线）该客户端发"请求检查点（带 KnownRevision）"；主机回分片数据；客户端用 revision 逐格拒旧它对这个 chunk 的确认版本未知 → 必须先对齐一次
chunk 离开某客户端窗口不要主机只把它从订阅者集合移除（停止投影）；不发卸载指令客户端是否保留由它自己决定；主机不需要为它省内存而指挥它
主机卸载 chunk（订阅者清空）不要释放内存；之后若又被需要 → 从存档重载卸载是主机内部缓存决策，不是同步事件
chunk 被改（有人在窗口内）要（增量）按反表查订阅者 → 合批广播改动格（每 tick 一批，玩家操作立即发）订阅者已确认基线，只需要差值
chunk 被改（没人在窗口内）不要（现在）什么都不发；改动留在世界里以后有人进来时，检查点会自动带上最新 revision
客户端报告自己 revision 落后要（补差）主机按它报的 KnownRevision 回增量或整块检查点这是"漏包"的唯一正确修法：让接收端说差在哪
客户端报的 revision 比主机还新要（纠正）回权威版本，客户端必须回滚到主机版本防止本地预测/回滚把脏数据坐实
客户端长时间不确认某 chunk要（超时重问）请求计时器触发重问；超过上限 → 收窄该客户端视野或断开避免"永远在等"的静默失败

revision 确认与陈旧副本

每个 (客户端, chunk) 一对数字
字段含义谁维护
chunk.revision该 chunk 内容版本，任何改动 +1（单调不回退）主机
client.known[chunk]这个客户端报告已应用的版本客户端上报 / 主机记录
client.confirmed[chunk]主机确认这个客户端已经到位的版本（检查点分片全部完成）主机
pending[chunk]正在传的检查点（已发第几片 / 共几片）主机
判定

known < revision → 发增量；known 缺失 → 发整块检查点；known > revision → 回权威版本要求回滚；confirmed == revision → 什么都不发。

为什么不用"加载事件"驱动

加载/卸载是主机内存管理的动作，与"客户端知道多少"无关。用事件驱动会在重载、抖动、丢包时反复误判；用版本差驱动，天然幂等、可重放、可超时重问。
