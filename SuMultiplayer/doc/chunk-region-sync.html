基础

先把三个尺度说清楚

格 → 区块 → 区域文件：同一个地图的三级包装，联机与存档分别用不同的那一级

格 / 区块 / 区域文件

俯视图：从一格方块放大到一个存档区域
为什么同步用区块而不是格

逐格索要太啰嗦：一个区块改动通常只有十几到几十格。按区块问一次「你现在是什么版本」，主机一次性把该区块的记录发回来即可。

为什么不用区域文件同步

一个区域文件覆盖 256×256 方块，远大于玩家的可视范围；按区域同步会传一大堆玩家根本看不到的地形。

区块是「整列」的

区块在垂直方向是全高的（Y=0..255），所以俯视图上一个小方格 = 一整个垂直柱子。

一次改动从发生到看见

主机侧：合并 → 排序 → 按订阅投影 → 分批下发
兴趣窗口

主机凭什么决定「这块改动发给谁」

每个客户端在主机侧有一张订阅表：中心 + 半径 → 一组区块

订阅表：中心 + 半径

中心由主机定，半径由客户端报

可播放：两个窗口移动时，一次改动发给谁

半径从哪来

客户端按自己的可视距离算出半径，用一条 Interest 阶段的消息上报；主机把它限制在 1..32 区块，记进订阅表。

窗口中心从哪来

主机用自己这边那个远端化身的权威坐标算中心。客户端无法把中心挪到别处，所以「开一个大窗口去看远处」这条路走不通。

可视距离 → 区块半径换算

半径 = ⌈可视距离 ÷ 16⌉，硬上限 32 区块
radius = ceil(max(visibility, 16) / 16) 再夹到 1 .. 32 窗口边长 = (2×radius+1)×16 方块

「新进入一个区块」到底意味着什么

不是重新下载地图，而是核对一次版本
步骤做什么
① 算窗口以玩家所在区块为中心、半径 R 的正方形 ⇒ 想订阅的区块集合
② 求差集与上一帧比较 ⇒ 新进入（要处理）/ 离开（丢弃记录）
③ 分类从没同步过 ⇒ 排队要检查点；同步过又回来 ⇒ 只探版本；1 秒内探过 ⇒ 跳过
④ 节流发出去重 + 限速（见 CPS02），主线程按预算发
⑤ 主机回只发该区块里改过的格子（十几到几十格）+ 一个完成标记
⑥ 本地落地作为优先批次应用；版本没对齐就留下待校验，下一轮再要
关键设计：世界包已经给了完整基线 加入时下载的整个世界是"某一刻的完整快照"，所以重新进入一个曾经同步过的区域，只需要核对版本，不需要重新拉内容。 否则玩家来回走动就会不断重复下载同一片地形。
离开窗口不等于删除地形 离开兴趣窗口只是主机不再把该区块的改动推给你（你也停止轮询它的版本）。 本地地形该保留的还是保留；下次回来时按版本补差。
检查点

区块检查点：一条三阶段的小协议

整个「走进新区域」的核心动作就是它；一段话可概括，但每一步都有讲究

Request → Data × N → Complete

只发「这个区块里改过的格子」，不发整块地形

可播放：一次检查点往返

阶段方向带上什么通道
Request客户端 → 主机区块坐标、本地已知版本 known可靠有序
Data主机 → 客户端格子坐标数组、权威值数组、区块版本、总批数、服务端 tick可靠无序
Complete主机 → 客户端区块版本、总批数可靠无序
Interest客户端 → 主机只有半径（不发坐标）原始消息

节流、去重与高水位

不让「要检查点」变成新的流量洪泛
去重

pending / queued同一区块不会同时排两次队；探测过的区块 1 秒内不再探。

限速

4 / 0.1s等于最多 40 个区块请求/秒，但正常稳定态远低于此。

刹车

32 / 16在途任务或检查点批过多时先停手，避免把可靠队列堵满。

主机到底发什么：实时值 + 真实批数

要点做法为什么
发什么值下发前把记录过的格子重读实时地形否则「已烧成空气」的负向改动会让消失的方块复活
报什么版本版本 = 这批真正发出去的最大序列号用主机自己的版本会把客户端记账推过它没收到的格子，之后被永久过滤
回看窗口下发下限往回看 64 个序列号覆盖「被 known 吞掉但其实没落地」的格子
批次大小每 32 格一个 Data 消息越大越容易卡在单包 / 流上
只发改动格没改过的区块回一个空 Complete一个区块通常只有十几到几十格有记录，代价可忽略
客户端落点作为优先批次应用，不推进全局序列屏障屏障只由常规广播推进

代码：ScMultiplayerTerrainHandlers.cs:652-772（主机侧）· 431-558（客户端侧）

自愈

丢了一格怎么办：三张自愈网

网络会丢包、有序流会停顿。这套系统不假设「一定送达」，而是每层都留了发现与补救的路径

第一张网：±2 区块校验环

每 0.5 秒挑一个区块核对版本，轮完 25 个约 12.5 秒

可播放：校验环轮流体检

第二张网：漏格补救与版本回压

时机动作目的
应用广播时标记没能落地的格子（按坐标记进缺失集合）把「格子层面的账」单独记下来
每 0.5 秒按格向主机要一次权威值（绕开区块版本过滤）直接把漏掉的格子补回来
同时把该区块上报的 known 压回缺失格之前的序列否则主机会认为「早就发过了」而永久跳过
缺失清空后该区块回到常规校验节奏不长期占用额外流量
一句话 版本是「区块层面」的账，漏格是「格子层面」的账：格子没落地，区块版本就不能前进。

第三张网：历史恢复（journal）

给"正在下载世界的客户端"补上它错过的那一段
为什么需要它

世界包是「下载开始那一刻」的快照，下载 + 导入实际要几十秒；这期间主机改的每一格，客户端都还没见过。

60 秒兜底

离线或已放弃的客户端不再占用内存；在线且有待恢复目标的客户端会把 journal 钉住，直到它追上。

上限保护

单条恢复消息最多携带 64 段区间，超出的分多次发，避免一条消息过大。

参数：TerrainRecoveryRetention = 60s、MaximumTerrainRecoveryRanges = 64 （ScMultiplayerRuntimeState.cs:894-895）；保留与裁剪逻辑：ScMultiplayerTerrainHandlers.cs:311-358。

重要的不是「一个数字」，而是作用域类型：全局 / 窗口 / 按距离分级

天气：状态全局，渲染只有身边几格

最容易误解的一项

可播放：相机移动时雨柱的创建与剔除

两个「改了没反应」的坑 ①「打开降雨/雾」会顺带把天气总开关打开，否则客户端根本不渲染； ②跳时间点前必须把时间模式切回 Changing，固定档位下改偏移看不到任何变化。

动物：按「离最近玩家多远」分级，没有统一半径

主机跑完整 AI，同步频率按距离与状态变

可播放：动物从远处走近，频率逐级升高

注意：这是「频率」分级，不是「范围」截断 主机对自己维护的动物都会同步（没有硬性距离切断），只是远处的更新得稀疏。 距离判定用的是「离最近的那个玩家」——所以一只动物身边没人时会掉到 2 Hz， 一旦有人靠近立刻升频。

地形变化：没有「半径」，只有「订阅」

主机改了什么不重要，重要的是「谁订了那块地」
