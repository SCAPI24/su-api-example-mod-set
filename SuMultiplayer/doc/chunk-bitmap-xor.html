用位图表示加载区域，用 XOR 求增量

你的构思里有两张表被混成了一张：兴趣位图（1 bit/chunk，管订阅与常驻）和 revision 表（管内容是否最新）。 XOR 是驱动订阅增量的正确工具；但"客户端是否最新"必须由 revision 回答 —— 否则窗口内的一次方块修改不会翻转任何一位。

但只到这一层

位图能表达什么、不能表达什么

一句话：比特没有"版本"
问题位图（1 bit/chunk）revision 表
这个 chunk 在不在任何人的窗口里？✓ 一次 OR 就知道不必要
谁要它？（要发给谁）✓ 逐客户端 AND/OR不必要
这一格该订阅还是退订？✓ XOR 直接给出不必要
主机该不该为它付内存？✓ 订阅计数 > 0不必要
客户端手上的内容是不是最新？✗ 位没变，但内容可能变了✓ 唯一能回答的
这个 chunk 被改过几次？✗✓ revision 计数
客户端报的版本比我新还是旧？✗✓ 比较 revision
关键坑：内容变化不翻转存在性位 "A 在 (12,7) 放了一个方块" —— 该 chunk 仍然在窗口里、仍然加载着：位图像素级完全没变，XOR 结果是 0。 如果同步由 XOR 触发，这次修改就永远不会发出去。
所以同步的触发器只能是「revision 差」，位图/XOR 只能用来管"谁该收到"和"要不要留内存"。

三个集合，别混成一个

你说的"主机只渲染自己所见"正是第三个集合

XOR 的三种正确用法

表达式含义用途
window_new XOR window_old这个客户端窗口变化前后不一致的格子订阅增量：置位的格子里，1→0 退订、0→1 订阅；只碰变化的格，不重扫 289 格
A XOR B两个客户端兴趣的对称差诊断"这一块只有 A 要"，以及判断某格订阅者是不是降到了 1
resident XOR render主机留着但不画的格子内存预算与"为别人多付了多少"的可视化
state_new XOR state_old（进阶）2 bit 状态平面的变化精确得到"哪些 (客户端,chunk) 需要发数据"（见 FRH03）
XOR 的真正价值：把 O(r²) 的扫描变成 O(变化数) 的更新 订阅计数不需要每次全量重算：只对 XOR 置位的格子做 count±1。步子与窗口的并集保持精确一致， 这就是"用位运算把范围表变成可增量维护的结构"。

行编码 vs 稠密位图

窗口是矩形，用稠密位图其实浪费
表示r=8（289 格）XOR 代价适用
矩形窗口（center + r）3 个整数无需 XOR，直接重算单客户端兴趣：最省，推荐给客户端窗口
行游程（每行 start+len）17×2 个数O(r) 行由矩形裁剪/挖洞得到的集合
稠密位图（1 bit/chunk）37 BO(r²/64) 字并集/反表/稀疏区域；推荐给"谁要这一格"
稀疏分块位图（64×64 一块）1 块 = 512 B按块命中世界很大、只在有人去过的地方分配
订阅计数（ushort/chunk）578 B只动变化格常驻判定；必须由 XOR 增量维护
你例子里的一个隐患 主机 01001001 / A 010 / B 001 宽度不同（8 / 3 / 3）。 位图必须绑定坐标系（原点 + 行宽），否则不同客户端的两行无法对齐、XOR 没有意义。 建议：对外只用「窗口矩形 + 半径」，内部按统一的分块坐标存位图。
新鲜度

"是否最新"必须另起一张表

位图管不着它

revision 表

每 chunk 一个版本，每客户端一个已知版本
表键 → 值更新时机回答什么
chunkRevision(cx,cz) → uint32该 chunk 任一格被改 → +1（单调）内容现在是什么版本
known(clientId, cx,cz) → uint32客户端上报"我已应用到此版本"客户端自称到哪了
confirmed(clientId, cx,cz) → uint32检查点分片全部传完主机确认它到哪了
pending(clientId, cx,cz) → (已发片, 总片)检查点发送过程正在传，避免重复发起
为什么 known 和 confirmed 要分开 known 是客户端说的（可能虚报、可能回滚），confirmed 是主机自己的账。 判定用 confirmed 保守推进、用 known 决定发增量还是整块 —— 两者不一致时以 confirmed 为准。

只用 XOR 会漏什么（可播放）

切一下开关，看漏同步是怎么发生的

2 bit 状态平面：把两张表合成一次 XOR

你想要的那张"表"，正确形态是这个
状态含义主机动作
00不在这个客户端的窗口里不退订则不用管；退订后计数 -1
01在窗口里，但还没有基线（未确认）等它请求检查点，或主动发起
10已确认且 confirmed == revision什么都不做（这是最常见的状态）
11已确认但落后（confirmed < revision）发增量
为什么是 2 bit 而不是 1 bit

1 bit 只能编码 2 个状态（在/不在），而"在"至少还要分"有没有基线""是否落后"。2 bit 刚好够，且整行仍是 2 的幂。

XOR 用在哪一层

分别对两个平面做 XOR：presence_new XOR presence_old 得订阅增量；fresh_old XOR fresh_new 得"哪几格需要发数据"。两平面分开算，不要混成一次 XOR。

// 每个 (客户端, chunk) 2 bit；整行按 ulong 打包
//   bits: 00 不在窗口 / 01 在窗口未基线 / 10 已最新 / 11 落后
var delta = windowNow.Xor(windowPrev);          // 存在性平面：订阅增量
var stale = freshNow.Xor(freshPrev);            // 新鲜度平面：需要发数据的格
// 订阅计数只用 delta 更新；发送名单只用 stale；两者互不干扰
foreach (var chunk in delta.SetBits())     refCount[chunk] += windowNow.Get(chunk) ? +1 : -1;
foreach (var chunk in stale.SetBits())     pending.Add(chunk);   // revision 差 → 补差

落到新 mod 的接口

纯逻辑模块，可单测，不碰引擎
// SuMultiplayer/Terrain/ChunkInterestTable.cs —— 纯逻辑，无引擎依赖
public sealed class ChunkInterestTable
{
    // 客户端窗口：矩形（最省），只在需要位运算时物化成 Bitmap
    InterestDelta UpdateClient(int clientId, int centerCx, int centerCz, int radius, long nowMs);

    // 常驻判定：计数 > 0 或滞回未过期
    bool IsResident(int cx, int cz, long nowMs);
    IReadOnlyList UnloadCandidates(long nowMs);   // 计数归零且滞回过期

    // 广播投影：一次查到订阅者（反表）
    IReadOnlyList<int> Subscribers(int cx, int cz);

    // 新鲜度（另一张表，别和位图混）
    uint Revision(int cx, int cz);
    void BumpRevision(int cx, int cz);                      // 有格被改
    void MarkKnown(int clientId, int cx, int cz, uint rev);
    void MarkConfirmed(int clientId, int cx, int cz, uint rev);
    bool NeedsSync(int clientId, int cx, int cz);            // confirmed < revision
    ChunkSyncState StateOf(int clientId, int cx, int cz);    // 2 bit: None/Unbased/Fresh/Stale
}

public readonly struct InterestDelta
{
    public IReadOnlyList<ChunkKey> Subscribed;    // windowNow XOR windowPrev 里 0→1
    public IReadOnlyList<ChunkKey> Unsubscribed;  // 1→0
    public IReadOnlyList<ChunkKey> UnloadReady;   // 计数归零 + 滞回过期
}
与已有组件的关系

它提供能力 terrain.interest；transfer 模块按它的 NeedsSync 决定发什么，hostAuthority 按 IsResident 决定留不留内存。
