# 模块解耦与"下线不影响其余"规范

> 目标：**任何一个模块被关闭、缺失、初始化失败或运行中熔断，其余系统照常运行**（只掉功能，不掉会话）。
> 实现落点：`Modules/ModuleContracts.cs`、`Modules/ModuleHost.cs`（编译通过，18 条断言见 §7）。

---

## 1. 「下线」有五种含义，要求各不相同

| # | 含义 | 期望行为 | 谁负责 |
|---|---|---|---|
| 1 | **未安装**（配置里就没这个模块） | 其它模块照常启动；依赖它的模块 `Unavailable` 或降级 | 宿主依赖解析 |
| 2 | **配置关闭** | 同上，且状态显示为 `Disabled` | 宿主 |
| 3 | **初始化失败**（`Attach` 抛异常） | 该模块 `Faulted` + 能力立刻撤回；依赖方下一轮降级 | 宿主 |
| 4 | **运行中熔断**（`Tick` 连续抛异常） | 计数 → 熔断 → 卸载 → 撤回能力 → 依赖方降级；**同一帧其它模块照常 Tick** | 宿主 |
| 5 | **依赖缺失**（它需要的模块先下线了） | 硬依赖 → `Unavailable`；软依赖 → 继续跑但标记 `Degraded` | 宿主 |

> 只有把第 5 种单独拿出来，才谈得上"下线不影响其余"；否则级联下线会假装成崩溃。

## 2. 七条硬规则

1. **模块之间零直接引用**：不允许 `ModuleA` 里 `new ModuleB` 或强转别的模块类型；只能通过能力与端口通信。
2. **依赖写成"能力"，不写"模块名"**：`RequiresCapabilities` / `PreferredCapabilities` 写的是 `terrain.sync` 这种能力 id，不关心谁提供、由几个模块提供。
3. **硬依赖只允许在同一条业务链内部**（如 `terrain.edit` → `terrain.sync`）；**跨域一律软依赖**，缺失即降级。
4. **端口一律 `TryGetPort`**：取不到就走降级分支；禁止在 `Attach` 或字段初始化里假设端口存在。
5. **状态所有权单一**：模块只清理自己的状态；禁止在 `Detach` 里清空全局或别人的东西。
6. **异常不许穿透**：模块的 `Tick` 里任何异常都由宿主隔离并计数，模块自己也要保证"抛了就什么都不改"（先校验后写）。
7. **必需能力显式登记**：`RequireEssential(capability)`；缺失时宿主如实上报 `EssentialMissing`，由上层决定"拒绝开局"而不是崩溃。

## 3. 能力命名约定

`<域>.<能力>`，短、稳定、不与协议字段混用：

```text
session.core        会话与连接（基础设施提供）
net.transport       传输端口
journal.sink        状态变化队列
terrain.sync        地形同步
terrain.authority   主机地形执行
player.state        玩家状态
player.action       玩家操作
entity.sync         实体同步
circuit.sync        电路同步
region.authority    领地执法
dataMod.authority   数据调整通道
ui.panels           面板
```

## 4. 模块宿主保证什么

| 保证 | 机制 |
|---|---|
| 依赖满足才装配 | 能力不动点求解；提供方先于依赖方 `Attach`（测试 §1） |
| 缺依赖不崩溃 | 硬依赖缺失 → `Unavailable`；软依赖缺失 → `Degraded`（测试 §2） |
| 单模块异常不外溢 | 逐模块 try/catch；连续失败达阈值熔断并撤回能力（测试 §3） |
| 下线是常态操作 | `SetEnabled(id, false)` → 逆序 `Detach` → 依赖方自动降级/恢复（测试 §4） |
| 端口可消失 | `TryGetPort` 返回 false，模块走降级而不抛异常（测试 §5） |
| 不会死循环 | 互相硬依赖 → 两者 `Unavailable`，解析有界（测试 §6） |
| 生命周期完整 | `Dispose` 逆序 Detach 并清空能力表（测试 §8） |

## 5. 宿主**不**解决什么（要靠纪律与契约测试）

- **共享物理世界**：地形、实体、容器是同一份数据，天然耦合；只能约定"只有一个权威执行者"（能力排他）。
- **唯一替换点**：原版 `SubsystemTerrain` / `SubsystemGameWidgets` 等一个进程只能被替换一次 → 这类能力必须**声明为独占**，第二个申请者直接 `Unavailable`。
- **可靠通道与带宽**：多个模块共用一个可靠队列 → 必须有每模块配额，否则一个模块的洪泛拖慢所有人。
- **协议字段**：能力差异必须在协议层协商（见 §6），不能靠"两端恰好装的一样"。
- **持久化 schema**：模块引入的存档字段必须可缺省，旧档缺字段 = 该模块 `Unavailable` 而不是加载失败。
- **帧预算**：一个模块吃满帧时间会让别人饿死；预算与高水位要写进模块契约。

## 6. 跨机下线：能力协商（最容易漏的一条）

主机与客户端的模块集合可能不同（一端装了领地、另一端没装）。要求：

1. 连接建立（协议闸门通过之后）交换**已上线能力集合**；
2. 客户端只对**双方都有**的能力显示入口；
3. 主机缺少某能力时，相关客户端请求收到明确的"能力不可用"拒绝（不是静默丢弃）；
4. 能力集合变化（热插拔/熔断）→ 广播一次能力增量，两端 UI 与降级路径同步更新。

> 否则会出现"客户端以为有、主机没有"的半状态：请求发出去没人处理，表现为"点了没反应"。

## 7. 验收判据（可执行）

| # | 用例 | 判据 |
|---|---|---|
| 1 | 正常装配 | 提供方先于依赖方 `Attach`；必需能力齐全 |
| 2 | 硬依赖缺失 | 该模块 `Unavailable`；无关模块照常 `Active` |
| 3 | 软依赖缺失 | 模块 `Active` 且 `Degraded=true` |
| 4 | 异常隔离 | 失败模块熔断前，其它模块 `Tick` 次数不受影响 |
| 5 | 熔断 | 达阈值 → `Faulted` + `Detach(Faulted)` + 能力撤回 |
| 6 | 级联 | 提供方下线 → 硬依赖方 `Unavailable`；重新上线 → 自动恢复 |
| 7 | 端口缺失 | `TryGetPort=false` 时走降级分支，不抛异常 |
| 8 | 循环依赖 | 双双 `Unavailable`，解析不死循环 |
| 9 | 必需缺失 | `EssentialMissing` 如实列出 |
| 10 | 收尾 | `Dispose` 逆序 Detach，能力表清空 |

（本次实测：10 组 / 18 条断言全部通过。）

## 8. 与状态变化队列的接线

- 每个模块只通过 `journal.sink` 能力写队列；队列不可用（未安装/熔断）→ 模块**继续运行**，只是不记录（禁止把日志当业务前置条件）。
- 模块状态变化（`StatusChanged`）与能力变化（`CapabilityChanged`）本身也要落一条 `Diagnostics` 记录，便于事后复盘"当时哪个模块不在线"。
