# ScMultiplayer 当前修改清单

本文件只保留尚未处理完成的任务，用于跨轮次继续工作。

- 新发现或未完成的问题立即加入本文件。
- 完成源码修改、Release 编译和要求的部署后，从本文件移入归档。
- 已完成任务的详细历史以归档、Git 提交和发布包为准。
- 每轮修改 ScMultiplayer 前先核对本文件，避免上下文压缩后遗漏任务。

## 当前稳定基线

- 当前正式源码和发布基线为 2.0.8；2.0.9 目前仅处于计划阶段。
- 已确认睡眠加速只由主机执行，客户端保持单步世界；睡眠后的世界时间与电路重锚保持现有实现。
- 已确认手动电路同步和电路运行恢复有效；新任务不得回改稳定的 Circuit Snapshot/Fence/Recovery 时序。
- 旧版 Joining Room、ACK、地形恢复、流量与睡眠修复记录已归档到
  [CURRENT-TASKS-ARCHIVE-2.0.7-2.0.8.md](CURRENT-TASKS-ARCHIVE-2.0.7-2.0.8.md)。

## 2.0.9 执行顺序

1. 先修复永久拒绝被错误重连，以及 `ProjectReady` 后加入屏障停滞；加入流程必须能够成功进入或明确退出，不能长期停留在 `Joining Room`。
2. 再完成不修改协议的动物额外逃跑逻辑移除，以及死亡主机情况下远程客户端角色自动唤醒。
3. 将经验球拾取、动物运动标志和确定性近战一起完成协议修订，统一构建同一份 2.0.9 包。
4. 树叶回弹先进行有界单坐标追踪，确认是挖掘拒绝还是旧 checkpoint 覆盖后再修改。
5. 使用 Release 构建，依次验证 Windows、华为、主机与双客户端，不提交临时诊断日志。

## 客户端在 ProjectReady 后长期停留 Joining Room（计划 2.0.9）

状态：待继续修复；用户反馈仍会卡在 `Joining Room`，只能重启游戏后再次进入

复现与日志结论：

- `17:44` 的失败是客户端 `2.0.7` 与主机 `2.0.8` 协议版本不兼容，主机正确拒绝；该次不属于
  加入屏障故障。
- `18:21` 的 `Rosnia Mear` 加入由主机返回永久拒绝
  `Host world snapshot is unavailable`，客户端却自动重试五次。永久拒绝应终止本次加入，
  关闭 `Joining Room` 并只显示一次明确错误，不能进入自动重连循环。
- `18:26` 的 ClientID 37 已下载并导入 `Ofbaistan`、发送 `ProjectReady`，随后也开始发送角色
  输入，说明世界实际上已经在对话框后运行；但该会话没有完成
  `CatchUpBatchComplete -> circuit bootstrap -> CatchUpBatchApplied -> ReadyToPlay`，因此界面
  始终停留在 `Joining Room`。
- ClientID 37 的 `ProjectReady` 时间为 `18:26:27.592`；首个最终未收到 ACK 的主机可靠包在
  `18:26:39.663` 才进入重试，而加入屏障此前已经停滞约 12 秒。客户端日志结束于
  `18:26:39.219`，现有证据不足以判断是 ACK 丢失触发重连，还是客户端退出/重连造成 ACK
  中断。
- `Rel=211`、`Rel=232` 只能作为断开时可靠队列健康指标，不能单独判定为根因；必须结合
  客户端生命周期、端点变化、重连状态和各加入屏障阶段时间关联分析。
- ClientID 34/37 的日志平台为 `Windows`、设备为 `Computer`；ClientID 37 对应服务端端点
  `111.58.132.152:27782`。没有额外的角色或端点证据前，不得把这些编号以及 M78 流量归因
  于华为平板。

实施方案：

- 将 `ConnectRefused` 分为永久拒绝与可恢复传输失败。版本不兼容、主机世界快照不可用等
  永久拒绝必须立即终止加入状态机、关闭 `Joining Room`、停止自动重连并显示一次原因；只有
  明确的临时网络失败才允许有界重试。
- Join catch-up 的普通 payload 改为只占 bulk 窗口，保留 join-critical 余量给 `ReadyToPlay`
  和电路快照完成包，避免世界已经可玩时仍被队列尾部卡住。
- 逐段核查并修复
  `ProjectReady -> CatchUpBatchComplete -> circuit bootstrap -> CatchUpBatchApplied -> ReadyToPlay`
  状态机，保证每个已接收阶段都能幂等前进，重复消息只确认而不重启整个加入流程。
- 加入屏障所需的小型控制消息不得被普通加入下载令牌、地形批次或可靠大包预留长期阻塞；
  为屏障控制消息保留有界的可靠发送余量，但不绕过可靠序列，也不能挤占电路同步所需冗余。
- Project 或 `SubsystemElectricity` 重新绑定时保留尚未完成的 circuit bootstrap 状态；新实例
  就绪后继续请求/应用当前 epoch 的快照，不能因短暂未绑定丢弃屏障边沿，也不能把旧 epoch
  应用到新 Project。
- 增加有界的阶段诊断，只记录状态变化和超时摘要：屏障收到、epoch 可用、快照请求、快照
  应用、`CatchUpBatchApplied` 和 Ready 确认。禁止逐帧输出；验证后移除详细临时诊断，仅保留
  低频故障阶段与断开原因。
- 断开分析继续关联 ACK 最后前进时间、可靠队列头包、客户端运行/退出、端点和重连代次；
  不允许仅凭 `Rel` 数量触发错误的全量恢复、重新加入或归责。

验收标准：

- 快速和限速地图下载后均能依次完成全部加入屏障，世界开始运行前关闭 `Joining Room`，不在
  对话框后接受角色操作。
- Windows 与华为分别执行首次加入、连续重复加入和双客户端交错加入，不出现某一端长期卡在
  `Joining Room`，也不出现 circuit recovery/fence 循环。
- 版本不兼容和 `Host world snapshot is unavailable` 等永久拒绝只显示一次并立即结束加入；
  不发生五次自动重试，也不残留正在加入状态。
- 强制退出客户端后，主机能按连接生命周期清理该客户端，其他在线客户端不受影响；重新启动
  后的新加入代次不继承旧 ACK、可靠队列或 circuit bootstrap 状态。
- 在可靠包丢失、重传和延迟条件下，小型屏障消息仍可前进；正常加入不提高静止流量、不触发
  全量地形恢复，也不破坏现有电路可靠序列。

日志证据：

  1570 行为 ClientID 37 加入，第 1579 行为 `ProjectReady`。
- 服务端 `Game.log`：约第 3383 行已排队 catch-up，约第 3385 行为后续 transport-stall 断开。

## 客户端拾取经验球不增加经验或没有音效（计划 2.0.9）

状态：已实施源码修复并完成 Release 构建，待 Windows/华为双端验证

复现现象：

- 客户端角色拾取经验球后，经验球会消失，但经验条没有立即增加，部分情况下看起来完全
  没有增加。
- 拾取客户端没有听到原版 `Audio/ExperienceCollected` 音效，或者收到的是普通物品拾取
  流程的结果。

源码结论：

- 原版 `SubsystemPickables.Update()` 对内容编号 `248` 使用专用分支，直接调用
  `ComponentLevel.AddExperience(count, playSound: true)`；经验球不进入背包。
- `HandlePickableAcquireRequest()` 当前只在主机端给远程角色增加经验，`Acquire` 回包没有
  携带经验数量或最终权威等级，客户端只能等待后续角色状态快照。
- `AuthoritativePlayerStateSnapshot` 只比较整数等级；未跨越整数级别的小数经验不会触发
  普通变化发送，只能依赖周期性强制快照。
- 主机原生拾取可能早于客户端 `RequestAcquire` 执行。经验球在
  `TryGetHostPickableCollector()` 中被明确排除，随后只广播 `Delete`，因此客户端只看到球
  消失，无法确定拾取者，也无法播放经验音效。
- 经验球的 `Acquire` 不含背包槽数据，当前客户端仍可能把空槽数组当作权威背包快照，
  干扰背包基线状态。

实施方案：

- 主机执行原版 `SubsystemPickables.Update()` 时临时排除网络远程角色，只保留主机本地和
  同设备本地角色参与原生拾取；网络客户端统一通过现有可靠 `RequestAcquire` 事务拾取，
  消除“主机原生拾取”和“客户端请求拾取”竞争。物理、碰撞、掉落寿命和水体效果仍由
  原版主机更新。
- `PickableSyncMessage.Acquire` 增加经验数量与拾取后权威等级，消息修订由 `2` 升为 `3`；
  主机只增加一次经验，并在可靠结果中返回最终等级。
- 客户端仅在自己是拾取者时应用主机最终等级、刷新升级提示，并按原版参数播放一次
  `Audio/ExperienceCollected`；其他客户端只移除经验球，不播放二维本地音效。
- 权威角色状态比较改为比较完整浮点等级，使经验变化不再被整数等级过滤；主机接受经验
  拾取后同时立即发布一次权威角色状态，作为持久状态和断线恢复兜底。
- 只有槽数组完整且非空时才应用 `Acquire` 中的背包快照；经验结果不能修改背包基线。
- 协议结构发生变化，下一正式包版本升为 `2.0.9`，主机和客户端必须使用同一包。

验收标准：

- 主机、Windows 客户端和华为客户端分别拾取单个及多个经验球，经验条立即按主机结果
  增加，且只有拾取设备播放一次原版经验音效。
- 跨整数等级时只出现一次升级提示和升级音效序列；普通经验拾取音效不重复。
- 其他客户端能看到经验球被正确吸收；重新加入房间后等级保持，不回退也不重复增加。
- 普通物品的拾取、部分拾取、背包已满、丢弃后短暂拾取保护和拾取声音保持现有行为。

## 远程客户端挖除树叶后短暂回弹（计划 2.0.9）

状态：已实施源码修复并完成 Release 构建，待 Windows/华为/远端服务器验证

复现现象：

- 客户端在远端服务器挖除树上的树叶后，部分树叶会在已经消失的位置快速重新出现，
  随后可能再次消失，表现为树叶生成或回弹。
- 该现象目前集中出现在树叶；需要在同一坐标上关联客户端挖掘请求、主机处理结果、实时
  terrain sequence 和 Chunk checkpoint，区分“主机首次拒绝后恢复”与“旧快照覆盖新结果”。

源码结论：

- 客户端先按原版 `ComponentMiner` 在本地预测挖掘，再由 `TerrainDigRequestMessage` 把
  `ExpectedValue`、`PredictedValue`、射线、工具和进度发送给主机。主机执行自己的射线、
  距离、工具和挖掘时间校验后，才调用原版 `SubsystemTerrain.DestroyCell()`。
- 主机当前要求 `authoritativeValue == message.ExpectedValue`，比较的是完整方块值。落叶树叶
  的 data 包含季节、季节进度和手动摇落状态，主机与客户端的加载或轮询时机不同就可能在
  内容编号相同的情况下 data 不同。此时第一次请求会被拒绝，客户端重试后可能按主机旧值
  恢复树叶，形成一次可见回弹。
- `TerrainDigResultMessage` 的直接结果只确认目标格，并作为无 sequence 的优先网络单元
  应用；主机稍后还会通过正常 terrain sequence 广播同一挖掘及邻近更新。
- Chunk checkpoint 在收到时带有 `Revision` 和 `ServerTick`，但
  `SuSubsystemTerrain.TryApplyNetworkCell()` 对 checkpoint 当前会绕过普通的逐格
  sequence/tick 旧值拒绝。若 checkpoint 在挖掘前生成、在挖掘成功后才应用，就可能用旧
  树叶覆盖已应用的空气；较新的实时 sequence 随后再次写入空气，形成“消失、回弹、再
  消失”。这条风险不限于树叶，但树叶季节更新和密集树冠会提高同一 Chunk 的更新与校验
  频率，使现象更容易暴露。

实施方案：

- 先增加有界、默认关闭的单坐标追踪，仅在复现窗口记录：客户端 request ID、完整
  expected/predicted value 及 contents/data，主机接受或拒绝原因、直接结果 tick，以及该格
  收到和应用的 live sequence、checkpoint revision/tick。确认后立即移除临时热路径日志。
- 把地形单元的权威新旧判断收敛成一个比较入口。Chunk checkpoint 只能补齐缺失状态，不能
  覆盖该格已经应用的更高 live sequence 或更新的直接操作结果；过期 checkpoint 仍应正常
  完成批次计数，不能导致 revision 永久重试。
- 客户端收到已接受的 `TerrainDigResult` 后，为目标格建立短期操作 fence，直到覆盖该结果
  的主机实时 sequence 到达；fence 期间拒绝 tick/revision 更旧或同 tick 但生成在操作之前的
  checkpoint，避免优先结果被旧快照反写。
- 挖掘请求仍由主机执行原版 `GetDigValue()`、掉落、粒子、工具损耗和统计。校验时先保留
  完整值精确匹配；对内容编号相同、仅主机权威动态 data 不同的树叶，使用主机当前值完成
  射线、耗时和挖掘结果计算，不信任客户端 data，也不因季节位差异拒绝合法挖掘。
- 保留落叶树叶在秋季后半段第一次交互时“摇落叶片并转为冬季状态”的原版语义；不能把
  原版仍有方块的状态误判为空气，也不能重复产生掉落物或粒子。
- 继续复用现有可靠挖掘请求去重、terrain journal、Chunk revision 和定向恢复，不增加全量
  Chunk 广播，不提高静止状态流量。

验收标准：

- Windows 和华为客户端分别在远端服务器连续挖除常绿树叶及春、夏、秋、冬状态的落叶
  树叶，主机接受后目标格不再回弹，另一客户端看到相同最终结果。
- 秋季可摇落树叶仍严格保持原版第一次摇落、后续挖除行为，掉落物、粒子和工具损耗各执行
  一次。
- 在同一 Chunk 主动触发 checkpoint、地形恢复或丢包重传后再挖树叶，旧 checkpoint 不得
  覆盖更新的挖掘结果；checkpoint 完成与 Chunk revision 仍能正常前进。
- 回归石头、木材、带 data 方块、快速连续挖掘和两客户端交叉挖掘，不能放宽距离、工具、
  射线或挖掘时间校验，也不能造成方块漏同步、重复掉落或额外稳定流量。

## 仓库放入/移除和地上掉落物拾取时网络流量明显升高（计划 2.0.9）

状态：已实施源码修复并完成 Release 构建，待 Windows/华为/远端复测

现象：

- 客户端把物品放入仓库、工作台或类似容器时，网络流量会明显升高。
- 客户端从地上移除掉落物时，也会出现类似的流量尖峰。

已知代码特征：

- `ContainerSyncMessage` 会携带整套 `SlotValues/SlotCounts`，以及 `BaseSlotValues/BaseSlotCounts`、
  `PlayerBaseSlotValues/PlayerBaseSlotCounts` 和 `PlayerSlotValues/PlayerSlotCounts`。
- 主机在容器交易中会发送完整状态和完整回包，而不是单槽增量。
- 地上掉落物拾取路径会反复发送 `RequestAcquire`，并在回包里携带权威背包快照与拾取音效边沿。

待确认点：

- 是单次事务包本身过大，还是客户端在容器未收敛前反复重试。
- 是容器同步、玩家装备同步，还是掉落物拾取链路共同造成尖峰。
- 是否需要把可稳定的交易改成更小粒度的增量确认，而不是继续广播整套槽数组。

## 客户端近战预测与主机命中随机结果不一致（计划 2.0.9）

状态：已实施源码修复并完成 Release 构建，待 Windows/华为复测

复现现象：

- 客户端本地角色攻击动物时立即显示 `Miss`，但主机权威动物实际已扣血；客户端随后收到的血量
  同步与本地刚才的命中反馈矛盾。
- 不能把客户端改成等待主机回包后才播放挥击、命中或 `Miss` 效果；近战必须继续在按键当帧有反馈。

源码结论：

- 原版 `ComponentMiner.Hit()` 每次先使用实例 `m_random` 生成 `0.8-1.2` 伤害倍率，再生成挥击音调，
  最后调用 `m_random.Bool(hitProbability)` 判断命中。命中概率还会根据目标速度是否小于 `0.05`
  乘以 `3`。
- 客户端保留 `Sum_playerInput.Hit` 执行一次原版本地预测；主机收到 `AnimalInteractionMessage`
  或 `HitRequest` 后，又在主机远程角色的 `ComponentMiner` 上执行一次原版 `Hit()`。两个
  `ComponentMiner.m_random` 的初始状态和消耗次数完全独立，因此同一次攻击会得到不同命中布尔值和伤害浮动。
- 当前 `MeleeHitResultMessage` 只在主机实际造成伤害时发送，不回复主机 `Miss`、冷却拒绝或空间校验拒绝。
  客户端收到主机命中结果后，又会在本地 `m_lastHitTime` 已经前进时直接忽略该结果。本地原版 `Hit()`
  即使判定为 `Miss` 也会先更新 `m_lastHitTime`，所以“客户端 Miss、主机命中”的确认必然被现有逻辑忽略。
- 客户端的请求限频约为 `0.36s`，而原版 `ComponentMiner.Hit()` 冷却约为 `0.66s`。客户端原版
  `Hit()` 可能因本地冷却直接返回，请求却已经发给主机；主机远程角色的 `m_lastHitTime` 时序不同，
  仍可能执行攻击，这是除随机数外的第二个不一致来源。

实施方案：

- 保留客户端即时攻击预测。在 `SuComponentInput` 已解析到网络动物或远程玩家目标后，当帧仍调用
  原版 `ComponentMiner.Hit()` 产生挥击、命中/`Miss`、粒子和动画，不等待网络往返。
- 新增单一职责的 `MeleeDeterminismPolicy`，由主机下发的会话盐、客户编号和连续攻击序号生成确定性种子；
  不接受客户端任意指定随机结果。客户端和主机端对同一攻击序号得到相同的 `Engine.Random` 初始状态。
- 在调用原版 `ComponentMiner.Hit()` 前保存 `m_random.State` 以及该调用内使用的原版静态冲击随机状态，
  临时切换到确定性攻击种子，调用结束后立即恢复。这样继续复用原版概率、伤害、工具损耗、统计和
  `AttackBody()` 逻辑，又不改变自动交互、其他角色或其他游戏随机序列。
- 客户端只在原版 `Hit()` 真正越过 `0.66s` 冷却并使 `m_lastHitTime` 前进后才发送请求；冷却期的按键不发送
  主机攻击。请求增加独立的客户模拟 tick，不再把攻击序号冒充为 `ClientTick`。
- 主机按客户编号验证连续攻击序号、模拟 tick 间隔、射线、距离、目标编号和权威物品栏，然后在主机远程角色上
  使用同一种子调用一次原版 `Hit()`。动物与玩家近战收敛到同一执行策略，不再一条直接调用、一条通过
  `playerInput.Hit` 间接调用。
- 命中概率中的“目标是否静止”使用客户端最后收到的主机权威速度分类，请求携带该快照 tick 和分类。
  主机只在它与对应 tick 的近期权威状态一致时使用，避免客户端展示速度和主机当前速度刚好跨过 `0.05`
  阈值时再次得到不同概率，同时不允许客户伪造“目标静止”来提高命中率。
- `MeleeHitResultMessage` 改为每个已处理序号都可靠回复，明确携带 `Hit`、`Miss`、`Rejected`
  结果、权威伤害、目标和服务器 tick。预测与主机一致时只确认序号，不重复播放挥击、冲击音、粒子或伤害数字；
  发生少数校验差异时才执行有界纠正。
- 主机仍是血量、伤害、击退、工具损耗和玩家统计的最终权威；确定性种子只是让合法客户端提前显示与主机相同的结果，
  不放宽主机的空间、冷却或物品校验。

验收标准：

- Windows 和华为客户端分别空手、持工具连续攻击静止与移动中的动物，每次本地 `Hit/Miss` 与主机扣血结果一致。
- 客户端攻击其他玩家时使用同一策略；命中音效、`Miss`、伤害数字和挥击动画在按键当帧出现，主机回包不重复播放。
- 快速连点、按住攻击、高延迟、丢包和重传下，每个攻击序号最多执行一次；冷却期按键不造成主机额外攻击。
- 更换手持物、工具损坏、等级不足、目标死亡或离开距离时，主机权威拒绝正确收敛，不重复损耗工具、重复扣血或永久保留预测伤害。
- 本项不修改原版 `ComponentMiner.Hit()` 源码，不改变原版命中率数值，不增加周期性流量；只在实际攻击时增加一次小型请求和结果。
